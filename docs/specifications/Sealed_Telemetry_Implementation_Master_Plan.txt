Working research title: Compromise-Resilient Evidence Reconciliation for OAuth Abuse in Serverless Applications
Source note: Based on the prior conversation’s Review-1 audit and proposed IBER architecture. The original presentation was not available for a fresh full-text cross-check in this generation; verify slide-specific wording and existing implementation status before marking any task complete.
1. Executive decision and boundaries
Objective: demonstrate that application-log suppression during simulated OAuth token replay does not necessarily eliminate independently observed evidence, and test whether invocation-bound, completeness-aware reconciliation improves detection compared with simpler log-based baselines.
Do not claim that an AWS Lambda extension is independent of a compromised Lambda process, that CloudTrail records arbitrary outbound SaaS requests, that a hash proves event truth, or that OAuth token revocation always takes effect immediately.
Definition of success
Review 2: deployed AWS Lambda application, controlled OAuth test API, legitimate request, disposable-token replay, suppressed application log, independent API-side audit event, correlation finding, timestamped demonstration and evidence.
Final capstone: IBER state machine, completeness windows, immutable evidence archive, safe response workflow, repeatable attack/fault scenarios, quantitative baselines, ablation study, cost/latency measurements, and documented limitations.
Non-goals: scraping live third-party credentials, production SaaS exploitation, universal attribution of all outbound traffic, guarantee of instantaneous detection, or perfect reconstruction from nonexistent evidence.

3. Logical architecture and data flows
Ingress: client -> API Gateway -> Lambda integration -> mock SaaS resource API. OAuth: mock authorization server issues short-lived scoped test token, stored in Secrets Manager for lab integration. Evidence: Lambda intent emitter, API Gateway access logs, supported CloudTrail events, Lambda platform telemetry, mock SaaS audit emitter. Collector: independently permissioned API Gateway/Lambda -> SQS -> normalizer -> DynamoDB correlation state and S3 Object Lock archive. Detection: EventBridge or SQS-triggered reconciler -> findings -> Step Functions response -> responder Lambda -> mock provider revoke/disable integration. Investigation: archive reader -> ordered timeline with confidence and gaps -> report.
Trust-sensitive architecture decisions
External SaaS audit record must originate at the test API service, not be copied from the compromised Lambda log.
For the first milestone, use a mock provider and mock SaaS API on separately permissioned infrastructure; real sandbox provider is optional later.
If intent is emitted solely by compromised application, it may be missing or fabricated. Detect against independently issued authorizations and external actions; label unverifiable cases inconclusive.
No guarantee of exact cross-provider request matching: use provider request ID where supported, else bounded identity/operation/resource/time matching with lower confidence.
Hash-chain ordering must be defined per collector partition or single writer; global ordering across parallel writers is not assumed.

6. Canonical event contracts
Evidence event v1 fields
event_id (UUID), schema_version, run_id, scenario_id, invocation_id (nullable), action_id (nullable), source_type, source_trust_tier, event_type, operation, resource_pseudonym, credential_fingerprint (HMAC), event_time_utc, collector_received_at_utc, provider_request_id (nullable), correlation_key (nullable), event_payload_hash, collector_receipt_id, source_health, integrity_version, trace_context (nullable).
Use UTC ISO-8601 timestamps. Keep event_time and received_at separate. Define source-specific required fields, schema validation, dead-letter handling, and duplicate behavior. Store raw original event and canonicalized normalized event separately; version normalization rules.
Detection finding v1
finding_id, run_id, affected_identity, evidence_event_ids[], classification (CONSISTENT, PENDING, SUSPICIOUS, CORROBORATED_SUSPECTED_ABUSE, INCONCLUSIVE), severity, rationale_codes[], missing_sources[], confidence_basis, decision_at, attack_ground_truth_reference (evaluation only), response_requested, response_verified_at, residual_uncertainty.
State transitions
PENDING -> CONSISTENT when required corroboration arrives; PENDING -> SUSPICIOUS when evidence contradicts authorization; PENDING -> INCONCLUSIVE if source unhealthy or coverage inadequate; SUSPICIOUS -> CORROBORATED_SUSPECTED_ABUSE when independently corroborated; late arrivals cause an auditable re-evaluation, not silent overwrite.

9. Algorithm specification and test cases
Matching precedence: (1) explicit provider_request_id and issued authorization ID, (2) invocation_id/action_id propagated through a trusted gateway where available, (3) bounded identity + operation + resource + time candidate set. Ambiguous matches remain ambiguous. Avoid treating correlation based only on time as definitive proof.
Deadline selection: estimate per-source arrival distributions on benign calibration runs; define D_source = chosen percentile + safety margin; record exact parameters and calibration data. Late events trigger revision and are measured as such. Do not hardcode a 5-second guarantee.

10. Research evaluation protocol
Research questions: RQ1 attack detection under suppressed logs; RQ2 false-positive robustness to benign telemetry faults; RQ3 latency/overhead/cost; RQ4 integrity and reconstruction accuracy. Ground truth must be generated by an isolated scenario runner, never inferred from detector output.
Baselines: B0 application logs only; B1 independent external audit only; B2 simple fixed-time missing-event rule; B3 full IBER. Ablations: remove completeness windows, invocation-bound matching, provider audit, integrity verification separately. Use separate calibration and held-out test runs; randomize execution order and document AWS region/time-of-day.
Metrics: precision, recall, F1, false-positive rate, inconclusive rate, detection p50/p95, evidence delivery p50/p95, containment verification time, reconstruction precision/order accuracy, modified-evidence detection rate, billed Lambda duration, cost per 1000 invocations. Report confidence intervals and denominators.
Initial engineering targets (not claims): >=90% recall on controlled replay scenarios, <=5% false-positive rate on held-out benign/fault runs, p95 <=10 seconds only where independent evidence arrives promptly; otherwise report observed bound and why.

14. Review-2 oral defense: anticipated questions
Is detection real time?
Near-real-time only when independent evidence arrives quickly; report measured end-to-end latency and distinguish detection after invocation.
Does everything finish before Lambda terminates?
No. The original invocation can finish while asynchronous ingestion, reconciliation, containment and forensics continue outside Lambda.
Why not CloudWatch alone?
Application logs may be suppressed; platform logs are incomplete for outbound SaaS operations; independent API-side evidence adds a different trust boundary.
What is novel?
A testable invocation-bound, completeness-aware reconciliation mechanism with explicit uncertainty and cross-source evidence, subject to prior-work comparison and ablations.
Can you prove the token was stolen?
The controlled scenario ground truth proves simulated exposure and replay; independent audit may corroborate unauthorized use but not always the theft mechanism.
Can you revoke immediately?
Only where the provider supports it; request and verify revocation separately. Do not equate API acknowledgment with immediate rejection.
What if both logs disappear?
Report inconclusive if no trustworthy witness exists; do not invent missing events.
What is the actual serverless benefit?
Event-driven processing and pay-per-use orchestration, while acknowledging cold starts, asynchronous delay and service cost.
